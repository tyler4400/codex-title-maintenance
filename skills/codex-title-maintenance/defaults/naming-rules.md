# 默认命名规则

## 目的

用简短、稳定的标题概括整个任务的主线，让用户能在列表中找到它。标题格式、允许前缀和日期来源以用户 `config.toml` 为准；此文件只规定语义选择。

## 选择短标题

- 综合用户最初目的、后续明确变更和已经形成的结果。最新一条错误、临时追问或工具输出不自动成为新主线。
- 优先使用具体对象和动作。中文短标题通常以 8–20 个字为宜；清楚准确比凑足字数更重要。保留有辨识度的英文名称、API、issue 或 PR 编号。
- 现有标题仍准确时保持稳定。只有主线实质变化、原题明显失真或不符合当前规则时才修改前缀或短标题。
- 不把“继续讨论”“已完成”“帮我看看”等缺乏辨识度的话作为标题主体。状态只有在帮助用户区分任务时才纳入。
- 不在主体中重复前缀或日期。日期由程序附加，模型不猜测日期。
- 标题不得泄露密钥、凭据、个人敏感信息或大段原文。

## 默认前缀：何时用，何时不用

若用户修改了配置中的前缀列表，以其实际列表为准。以下解释只适用于仍被允许的前缀。先判断用户想完成的主要结果，再选前缀；不要根据最后一条消息、文件类型或任务所处阶段机械切换。

| 前缀 | 用 | 不用 |
|---|---|---|
| 探索 | 搞清已有物怎么用、是什么，或理解一个尚未收敛的新方向 | 在 A、B 间比较并决定选哪个，用 `选型`；只读一份单点说明书仍属于 `探索`，不因有“说明”二字改成其他前缀 |
| 选型 | 对比候选方案、产品或技术，权衡取舍、值不值得、最终怎么选 | 单点了解某个对象怎么工作，用 `探索` |
| 环境 | 安装、接入、代理、依赖、开发机或运行环境故障，以及把工具链连通 | 改既有规则、偏好或配置，用 `设置`；动手写代码，用 `实现` |
| 设置 | rule、hook、标题规范、偏好、权限、持久化和既有工具配置 | 接线、安装插件或让外部工具可用，用 `环境` |
| 方案 | 讨论怎么设计、如何推进，或把需求、Jira 和约束整理成可执行计划 | 已进入具体落地或写代码，用 `实现` |
| 实现 | 动手制作脚本、助手、skill、工具能力或非业务代码的落地工作 | 纯讨论设计，用 `方案`；写明确的业务 feature，用 `功能` |
| 功能 | 动手实现或调整业务 feature、业务流程和业务代码 | 修复已确认的业务缺陷，用 `Bug`；不是业务功能代码的通用工具实现，用 `实现` |
| Bug | 报错、失败、告警、本机故障，或定位和修复已知缺陷 | 测试本身还没写完，用 `测试` |
| 测试 | 写测试、造数据、设计或评审测试用例，以及执行测试的正常工作 | 测试已经失败且主线变成定位修复，用 `Bug` |
| PR | 已有 PR 的描述、review、CI、反馈和合并 | 尚未进入 PR 流程的设计或编码，用 `方案` 或 `实现` |
| 检索 | 查找某条 chat、跨项目回忆、历史记录、文件或已知资料 | 了解一个新产品或陌生概念，用 `探索` |
| Git | 分支、stash、clone、exclude、提交、冲突和版本历史操作 | 安装 Git 工具或配置开发环境，用 `环境` |
| 求知 | 非专业知识、学习、天文地理、教学、话术、简历和面试 | 对专业产品、技术或系统做调研，用 `探索` |
| 生活 | 家庭、消费和非开发日常事务 | 开发机或软件发生故障，用 `Bug` |

多个前缀都适合时，选择最能说明用户主要目的的一个。若主线从“研究如何做”明确转成“正在制作”，可以从 `探索` 或 `方案` 变为 `实现`；不要只因处理了一条错误、跑了一次测试或创建了一个分支就频繁改前缀。

## 示例

- `探索｜重命名标题｜0916`：调研自动重命名能力和可行性。
- `方案｜任务标题增量维护｜0917`：讨论维护机制、状态和调度。
- `Bug｜修复重复邮件发送｜0917`：任务主线是定位和修复重复发送。

示例的日期仅用于说明格式，不是实际执行时应使用的日期。
